--------------------------------------------------------------------------------
1. PROJECT PURPOSE
--------------------------------------------------------------------------------
Portal inYice is a multi-tenant travel-agency finance and order workspace. The
current product focus is:

- Agency registration and tenant/company setup
- Company profile and company user management
- Customer and vendor master data
- GDS-assisted voucher capture
- Quote/order bookkeeping
- Order-to-invoice conversion
- Customer receipts and customer payments
- Vendor receipts and vendor payments
- Cash/bank ledger movement
- Reports, statements, and reference search
- Public voucher/invoice sharing by secure token
- Internal provider operations for support and account control

This scope continues to exclude expense management, attendance, shift
management, payroll, and broad HR workflows.

--------------------------------------------------------------------------------
2. CURRENT IMPLEMENTATION STACK
--------------------------------------------------------------------------------
The current application is a single Laravel and React project.

- Backend: Laravel 13.11, PHP 8.4 runtime, Laravel Sanctum
- Frontend: React 18, Ant Design 6, Vite 8
- Database: Laravel migrations for relational storage
- Runtime support: local PHP/Vite and Docker compose files
- API base path: /api/v1

--------------------------------------------------------------------------------
3. TENANCY, COMPANY PROFILE, AND LIMITS
--------------------------------------------------------------------------------
Each agency operates inside its own tenant and company scope. Business records
are tenant-scoped and, where relevant, company-scoped.

Company setup includes:

- Legal/display name
- Email, phone, address, and country
- Base currency
- Default timezone
- Monthly invoice limit
- User limit
- Optional logo/footer logo paths
- Active/blocked status

The internal provider portal can inspect non-internal companies, update monthly
invoice and user limits, and block or unblock companies.

--------------------------------------------------------------------------------
4. COMPANY USERS AND ROLES
--------------------------------------------------------------------------------
Tenant roles:

- Owner
- Admin
- Sales
- Accounts

The initial registration user is assigned Owner. Owner users satisfy admin-level
checks in application logic. Owner/admin users can create company users with
Admin, Sales, or Accounts roles until the company user limit is reached.

System/provider roles:

- Super Admin
- InYice Admin
- Support Executive

System users enter the internal portal rather than the normal agency workspace.
System-role middleware controls internal access, and selected sensitive internal
actions are limited to Super Admin.

--------------------------------------------------------------------------------
5. CUSTOMER AND VENDOR DATA MODEL
--------------------------------------------------------------------------------
The platform supports both B2B agency-to-agency records and agency-local B2C
records.

Customer records support:

- B2B/B2C type
- Contact and address details
- Postal code and tax id
- Currency code
- Optional B2B agency link

Vendor records support:

- B2B/B2C type
- Contact and address details
- Postal code and tax id
- Currency code
- Optional B2B agency link
- Payment terms

Customers and vendors are reusable across order creation, voucher services,
receipts, payments, reports, statements, and reference search.

--------------------------------------------------------------------------------
6. ORDER, VOUCHER, AND GDS WORKFLOW
--------------------------------------------------------------------------------
The core order workflow starts in the Create Order workspace:

1. Paste and parse GDS text or enter voucher details manually.
2. Review passenger, flight, service, pricing, and vendor-cost data.
3. Select customer, optional vendor, currency, status, and notes.
4. Create a quote/order.
5. Convert the order to an invoice when ready.

Voucher data includes:

- Voucher number and issue date
- Travel/package details
- Booking reference and GDS source
- Emergency/company/executive contact details
- Active service sections
- Passengers
- Flights
- Per-passenger pricing
- Visa, transfer, ziarat, hotel, and other service rows

Orders store the full voucher payload in metadata. Searchable voucher fields are
also copied to order columns for list/report/search use.

GDS parsing currently supports backend parsing for Sabre and Galileo. The
frontend can also label Amadeus or Other source data for manual workflows.

--------------------------------------------------------------------------------
7. ORDER LIFECYCLE
--------------------------------------------------------------------------------
Current order statuses include:

- quote
- order
- cancel
- invoice
- void
- refund_request
- refund
- partial_refund
- paid
- partial_paid

Current model transitions:

- quote -> order, cancel, invoice
- order -> cancel, invoice
- invoice -> void, refund_request, refund, partial_refund, paid, partial_paid
- refund_request -> partial_refund, refund, cancel
- partial_refund -> refund
- partial_paid -> paid

Order history and audit-support models exist for lifecycle accountability.
Orders use soft deletes. Editing an already-invoiced order may cancel the current
invoice and create a replacement order to preserve financial history.

--------------------------------------------------------------------------------
8. INVOICING
--------------------------------------------------------------------------------
Orders can be converted into invoices. Invoice creation copies generated order
items into invoice lines and enforces the company's monthly invoice limit.

Invoice statuses include:

- draft
- issued
- sent
- partial_paid
- paid
- overdue
- void
- cancel

Invoice operations include:

- Create from order
- List and view detail
- Mark as sent
- Add discount through a negative invoice line
- Void
- Cancel
- Share and revoke public sharing
- Check aging status

--------------------------------------------------------------------------------
9. RECEIPTS, PAYMENTS, AND LEDGER
--------------------------------------------------------------------------------
Financial movement uses direction-based terminology.

Receipts are money received:

- Customer receipts settle one or many customer invoices.
- Customer advances are supported.
- Vendor receipts record money received from vendors.

Payments are money paid:

- Vendor payments settle one or many payable orders.
- Customer payments record money paid back to customers, including refunds.

Cash and bank accounts can be linked to receipts/payments. Ledger entries keep
account balances synchronized when an account is supplied.

--------------------------------------------------------------------------------
10. REPORTS, STATEMENTS, AND SEARCH
--------------------------------------------------------------------------------
Current reporting and lookup areas include:

- Dashboard upcoming data
- Aging Report
- Revenue Report
- Profit Report
- Receipt Report
- Payment Report
- Cancelled Report
- Customer Summary API
- Customer Statement
- Vendor Statement
- Reference Search

Reports and statements use the signed-in user's company automatically. Profit
Report uses invoiced order revenue minus supplier costs from order_vendor_costs.
Vendor-wise profit allocates order revenue by vendor cost share to avoid
double-counting multi-vendor orders.

Reference Search can search tenant/company-scoped orders, invoices, customers,
vendors, receipts, and payments by references, passenger/customer fields, dates,
statuses, and amount ranges.

--------------------------------------------------------------------------------
11. PUBLIC SHARING
--------------------------------------------------------------------------------
Authenticated users with permission can create public share links for:

- Vouchers/orders
- Invoices

Public shared reads use long random share tokens and return limited record data.
Share tokens can be revoked from the authenticated workspace.

--------------------------------------------------------------------------------
12. INTERNAL PROVIDER PORTAL
--------------------------------------------------------------------------------
System users are routed to the internal portal. Current internal capabilities
include:

- List/search customer companies
- Inspect company usage and recent records
- View company users
- Update company limits
- Block/unblock companies
- Manage internal users
- Reset internal user passwords
- View selected orders and invoices across tenants

The provider tenant is kept separate from normal customer company listings.

--------------------------------------------------------------------------------
13. TENANT ISOLATION AND AUDIT CONTROL
--------------------------------------------------------------------------------
Data visibility rules remain strict:

- Agency users cannot access another agency's tenant/company records.
- Company-specific screens use the signed-in user's company.
- Public shared-token endpoints are the controlled external visibility path.
- Internal portal cross-tenant visibility is restricted to system roles.

Audit goals:

- Track who performed important actions.
- Track what changed.
- Track when it changed.
- Preserve financial history for posted invoices and edited invoiced orders.
